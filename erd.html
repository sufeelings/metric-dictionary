상담 만족도 ERD

csat_survey · support_tickets · agents · customers. 컬럼은 키와 만족도 계산에 쓰는 것만 넣었습니다. 선은 실제 값이 조인되는 것만 그었습니다.

  customers {

  }
  agents {
    VARCHAR agent_id PK

  support_tickets {
    VARCHAR ticket_id PK
    VARCHAR customer_id FK
    VARCHAR agent_id FK
  }
  csat_survey {
    VARCHAR survey_id PK
    VARCHAR ticket_id FK
    VARCHAR customer_id FK
    DATE survey_date "응답일 (집계 기간 기준)"
    INTEGER csat "만족도 점수 1~5"
  }

테이블별 한 행의 뜻

테이블한 행행 수키
csat_survey상담 뒤 받은 만족도 설문 응답 1건입니다. 문의 1건마다 응답은 많아야 1건입니다.9,687survey_id
support_tickets고객 문의(상담) 1건입니다. 담당 상담원은 1명입니다.32,789ticket_id
agents상담원 1명입니다.120agent_id
customers고객 1명입니다.50,000customer_id

선을 확인한 방법

선확인 결과 (data/*.parquet 를 DuckDB로 조회)
csat_survey.ticket_id → support_tickets.ticket_id설문 9,687건이 모두 문의와 매칭됩니다. 문의 1건에 설문은 최대 1건이고, 설문일은 문의일로부터 1~3일 뒤입니다.
support_tickets.agent_id → agents.agent_id문의 32,789건이 모두 상담원과 매칭됩니다. 상담원 120명 모두 문의를 1건 이상 맡았습니다.
support_tickets.customer_id → customers.customer_id문의 32,789건이 모두 고객과 매칭됩니다(고객 23,398명). 문의가 없는 고객도 있습니다.
csat_survey.customer_id → customers.customer_id설문 9,687건이 모두 고객과 매칭됩니다. 이 값은 해당 문의의 customer_id와 9,687건 모두 같아서, 문의를 거쳐 가는 경로와 같은 고객을 가리킵니다.

metrics/ 에는 아직 '상담 만족도' 정의서가 없습니다. 그래서 만족도 컬럼은 csat와 survey_date로 잡았는데, 이것은 가정입니다. 정의서가 생기면 그에 맞춰 바꿔야 합니다.
