# 정의점검

정의서는 사람이 정한 문장(`elements`)과, 그 문장대로 세는 SQL(`sql`)을 함께 담고 있다.
둘이 다른 일을 하면 카드에 찍히는 숫자는 문장과 다른 것을 세게 되고, 아무도 눈치채지 못한다.
이 스킬은 그 어긋남을 찾아서 **보여 주기만** 한다.

## 하지 않는 것

- **파일을 고치지 않는다.** 정의서도, index.json 도, 다른 어떤 파일도 만들거나 바꾸지 않는다.
- **문장과 SQL 중 어느 쪽이 맞는지 정하지 않는다.** 정의는 사람이 정한다.
  어긋남을 보여 줄 뿐이고, 고치는 방향을 권하지도 않는다. 사람이 결정을 내릴 때 필요한 사실만 적는다.

## 대상 고르기

- 인자(`$ARGUMENTS`)가 비어 있으면 `metrics/index.json` 에 있는 정의서를 모두 본다.
  `metrics/` 폴더에는 있지만 index.json 에 없는 정의서가 있으면 그 사실도 따로 한 줄로 알린다.
- 인자가 있으면 정의서의 `name`(예: 상담 만족도) · `id`(예: support_csat_rate) · 파일 이름(예: 상담_만족도.json) 중 하나와 맞는 것만 본다.
  맞는 정의서가 없으면 점검하지 말고, 있는 정의서 이름 목록을 보여 주며 어느 것인지 묻는다.

## 점검하는 법

### SQL이 있는 정의서 (`kind` 가 base 등)

요소 다섯 개마다 문장이 말하는 대상과 SQL이 실제로 세는 대상을 나란히 놓고 비교한다.

| 요소 | 문장에서 볼 것 | SQL에서 볼 것 |
|---|---|---|
| numerator | 무엇을 세거나 더하는가, 어떤 조건을 만족해야 하는가 | `numerator` 열의 집계식과 FILTER · WHERE · JOIN 조건 |
| denominator | 무엇으로 나누는가, 없다면 "없음" | `denominator` 열이 있는가, 그 집계식과 조건 |
| period | 기준 날짜 컬럼, 경계(1일~말일, 말일 기준 등) | 날짜 조건에 쓰인 컬럼과 `{month}` · `{month_start}` · `{month_end}` 비교 방식(`<=` 인지 `<` 인지까지) |
| filter | 대상에서 거르는 조건 | WHERE · JOIN 으로 대상이 좁혀지는 곳 |
| exclusion | 빼는 대상 | 그 대상이 실제로 빠지는가 |

비교할 때 지킬 것:

- **요소는 함께 읽는다.** 예를 들어 분자 문장에는 조건이 없지만 제외 문장이 "월말 유지 고객만 본다"고 적었다면, SQL이 그 조건을 거는 것은 어긋남이 아니다.
  정의서 전체 문장으로 보아 SQL과 같은 일을 하면 어긋남으로 올리지 않는다.
  다만 문장 하나만 읽으면 오해할 만한 곳은 표 밖에 "어긋남은 아니지만 오해할 수 있는 곳"으로 짧게 적는다.
- **SQL이 문장대로 세려면 데이터에서 참이어야 하는 전제는 조회로 확인한다.** 짐작으로 넘기지 않는다.
  확인할 것의 예:
  - 조인한 쪽 키가 중복되지 않는가 (중복되면 행이 복제되어 COUNT · SUM 이 부푼다)
  - `{month}` 와 비교하는 컬럼의 값 형식이 같은가 (예: `'2025-12'`)
  - 조건에 쓰인 컬럼에 NULL 이 있는가 (NULL 은 조건에서 조용히 빠진다)
  - `COUNT(*)` 가 문장이 말하는 단위(문의 1건, 고객 1명)와 같은 단위를 세는가
  - 데이터는 `data/*.parquet` 에 있고, `schema.json` 에 테이블마다 한 행의 뜻(grain)이 적혀 있다.
    조회는 DuckDB 로 읽기만 한다. 전제가 깨지면 그것이 곧 어긋남이다.
- **`rejected`(버린 정의)의 SQL 은 점검하지 않는다.** 일부러 다르게 센 SQL 이라 문장과 다른 것이 당연하다.

### SQL 없이 다른 정의서를 가져다 쓰는 정의서 (`kind: "derived"`)

`inputs` 에 적힌 id 마다, 그 `id` 를 가진 정의서가 `metrics/` 에 실제로 있는지만 본다.
없는 id 가 있으면 표에 한 행으로 올린다(요소 칸에는 `inputs`, SQL이 하는 것 칸에는 "해당 id 의 정의서가 없음").
계산식이나 문장 내용은 대조하지 않는다.

## 답의 모양

첫 줄에 점검한 정의서의 id 를 모두 적는다.

어긋남이 있으면 이 표 하나로 보여 준다. 어긋난 곳 하나가 한 행이다.

| 정의서 | 요소 | 문장이 말하는 것 | SQL이 하는 것 |
|---|---|---|---|
| 상담 만족도 (support_csat_rate) | period | 문의 접수일 기준 | 설문 응답일(survey_date)로 월을 자른다 |

어긋남이 없으면 표를 만들지 말고 "어긋남 없음" 이라고 분명히 쓴다.
그 아래에 짧게:

- 데이터로 확인한 전제와 결과
- 가져다 쓰는 정의서의 확인 결과
- 어긋남은 아니지만 오해할 수 있는 곳 (있을 때만)

을 적는다. 고치자는 제안은 넣지 않는다.
